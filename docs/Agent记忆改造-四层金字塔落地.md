# Agent 记忆改造：把 Claude 的四层金字塔落到本机

> 触发：Anthropic《The components of agent memory》公开（四层金字塔 + 离线 Dreaming）。
> 本文不是读后感，而是**把它的判据对到本机已有资产上**，给出可执行的三阶段改造。
>
> 适用范围：本机 DSH（DeepSeek Harness）+ 仓库级文档体系（weflow-cli 等）。
> 不涉及：模型权重、训练。

---

## 0. 一句话结论

**你这边缺的不是"存记忆的地方"，而是"记忆的层级"和"离线对账"。**

现状是：原始流水有（202 个会话压缩日志）、项目级规则有（`docs/DECISIONS.md` 那套）、但——

- **没有一层专门承载"跨项目的隐性规则"**（现在散落在各个 AGENTS.md 和脑内）；
- **没有离线对账**，所以错误笔记会一直被后人当真理（本会话就发生过：把"npm 409 staged"误判成"需要人工批准"，查了 token 类型、建议换 Automation token，最后发现只是 registry 同步延迟）。

## 1. 本机现状盘点（对照四层）

| 层 | Claude 的定义 | 本机**已有的** | 缺口 |
| --- | --- | --- | --- |
| L1 原始流水 | 无损 transcript，唯一 ground truth | `dsh/home/sessions/**/session.v4.jsonl.zstd`（202 个）、`dsh/home/attachments/` | 没有**可检索**的形态（压缩、无索引） |
| L2 记忆笔记 | 会话中标注的显著观察 | `dsh_memory`（facts.jsonl / notes.md）、各仓库 `AGENTS.md` 的"踩过的坑" | 写入**靠自觉**，无触发点；无去重 |
| L3 知识地图 | 离线归纳成结构化 Wiki | `weflow-cli/docs/{PROJECT_STATE,DECISIONS,VERSION_METHODS}.md`、`output/wechat-vault/Wiki/Concepts/`、`zhaowen-dsh/docs/` | 只覆盖**单个项目**；没有跨项目层 |
| L4 开局注入 | 启动时预加载的轻量索引 | `AGENTS.md` / `CLAUDE.md` / 会话启动注入 | 没有**容量上限**，越写越长 |

**判断：L1 和 L3 是有的（甚至很好），L2 是散的，L4 是无节制的。**

## 2. 第一判据：记什么（这条最容易做错）

Anthropic 的判据是**易变事实 vs 隐性规则**。落到本机：

### 不该记（易变事实）

| 例子（本会话真实出现） | 为什么不该记 |
| --- | --- |
| 微信 Linux 4.1.13.26 的 `key`/`salt` 特征 | 版本一换就作废 |
| 某个 DB 现在有多少行、某个目录现在多大 | 看一眼比查记忆便宜且准 |
| 当前 npm 上是什么版本 | 一条命令就知道 |

### 该记（隐性规则）

| 例子（本会话真实踩过） | 为什么是规则 |
| --- | --- |
| **负结论必须有正对照**，且对照要写进脚本 | 否则"0 命中"是假的（我们靠这条才发现扫描器有效） |
| **`immutable=1` 读不到热 WAL**；有 WAL 时读副本 | 结构性知识，不会因版本变化失效 |
| **`catch syscall` 能中、libc 断点不中**（客户端直接发 syscall） | 这类"路不通，是因为工具层选错了"极难重新发现 |
| **回复前必须先读 `output/REPLY-RULES.md`** | 我违反过一次（用了昵称、写了未发布计划） |
| **npm `409 staged` 不是失败**，等几分钟即可 | 否则会误导用户去点批准 |
| **临时副本要落 `temp_root()`**，别用 `mkdtemp()` 默认值 | 进程内缓存首次取值，只设 `TEMP` 不生效 |

**一句话：只记"下次还会再犯的错"，和"重来会很贵的发现"。**

## 3. 目标架构

```
L4  开局注入         ≤ 200 行 / ≤ 25 KB        ← 只放索引：我有哪些知识、在哪
     ↑ 由 Dreaming 生成
L3  知识地图         跨项目 Wiki + 项目级 docs   ← 结构化、双向链接、可 lint
     ↑ 由 Dreaming 合并
L2  记忆笔记         会话中即时写入的教训       ← 平铺 Markdown/jsonl、带来源
     ↑ 由规则触发
L1  原始流水         会话 jsonl（已有 202 个）   ← 只追加，永不改写
```

### 各层的写入者与节奏

| 层 | 谁写 | 何时 | 容量 |
| --- | --- | --- | --- |
| L1 | 运行时自动 | 每轮 | 无限（压缩存储） |
| L2 | 我（agent）+ 你 | 会话中命中"教训"时 | 单个文件 ≤ 200 条，超出折叠进 L3 |
| L3 | **Dreaming 离线任务** | 每周或每 N 次会话 | 每页 ≤ 200 行 |
| L4 | Dreaming 生成 | 同上 | **硬上限 200 行 / 25 KB** |

---

## 4. Dreaming：本机的"离线对账"

这是整套东西里**唯一真正新增的组件**，也是最值钱的一环。

### 4.1 输入

1. `dsh/home/sessions/**/session.v4.jsonl.zstd`（自上次 Dreaming 以来的新会话）
2. 现有 L2 笔记（待校验对象）
3. **对照源**：L1 流水原文（用于推翻写错的笔记）

### 4.2 三个动作（对应文章的三条）

| 动作 | 具体做什么 | 本机例子 |
| --- | --- | --- |
| **① 事实对账** | 每条 L2 笔记回查流水：当时真的验证过吗？还是猜测被记成了结论 | "npm 409 需要人工批准"这条，流水里根本没有证据，只有一次失败重试 → 改写成"409 是处理中，等 3-5 分钟再查 registry" |
| **② 拓扑修补** | 死链、孤儿页、重复页、过期页 | `docs/LINUX.md` 里"版本探测 ❌"早在实现后仍是 ❌（本次已修）；`ARCHITECTURE.md` 的计数落后于磁盘 |
| **③ 剪枝** | 访问频次 + 置信度衰减，淘汰过期 | 微信 4.2 落库下降那条已定案 → 保留结论，删掉中间推导 |

### 4.3 输出

- 改写后的 L2 → 合并进 L3
- 重新生成 L4（≤ 200 行索引）
- 一份 `dreaming-report.md`：**改了什么、为什么改、依据哪条流水**（必须可回溯）

### 4.4 成本控制

- 全量重写 L3 太贵 → **只处理"有新流水的项目"**
- 对账只挑**结论型笔记**（含"不能/必须/永远/一定"的句子），不逐条读
- 单次预算：≤ 30 分钟、≤ 20 次模型调用

## 5. 三阶段落地（每阶段可验收）

### 阶段一：把 L2 立起来（1 天）

| 动作 | 验收 |
| --- | --- |
| 建 `dsh/home/plugins/dsh-agent-supervisor/memory/`（`dsh_memory` 的落点） | `dsh_memory list` 有输出 |
| 定一条**写入触发规则**：出现以下任一，立即写一条 | 连续 3 次会话都有新条目 |
| ① 负结论（"0 命中/不支持/没找到"）② 用户纠正我 ③ 排查超过 3 步才定位 ④ 一个假设被证伪 | |

### 阶段二：Dreaming 最小版（1 周）

写一个脚本 `scripts/dreaming.py`：

```
1. 解压新会话 → 提取"结论型句子"（正则：必须/不能/永远/不是/因为）
2. 每条回查流水：原文里有没有对应的验证动作？
3. 没有 → 标记"未验证"，降级为"待确认"
4. 有 → 保留，附上 commit hash / 命令 / 输出片段
5. 输出 report + 更新 L2
```

**验收判据**：拿本会话做一次回放，Dreaming 应该能抓出至少 2 条"没验证就当结论"的笔记（例如 npm 409、以及"gdb 断点能中"其实一开始是错的）。

### 阶段三：L3/L4 自动化（2-3 周）

- L3：把 `weflow-cli/docs` 那套模式**泛化成跨项目**——`docs/KNOWLEDGE/<领域>.md`，每页带"最后验证时间 + 依据"
- L4：生成 ≤ 200 行索引，替换现在无上限的 `AGENTS.md` 注入
- 加一个守卫测试（照 `test/architecture-counts.test.ts` 的写法）：**L4 超过 200 行就红**

## 7. 边界：绝对不记的东西

按仓库 `AGENTS.md` 与 `SECURITY.md`：

- 真实路径、`wxid`、聊天内容、密钥、token
- 用户设备标识、SSH 主机名与 IP
- 任何"本地处理 = 法律/账号安全保证"的表述

**L1 流水本身包含这些**（会话里出现过），所以：L1 只留本机、不导出；L2/L3 写入前必须脱敏。

---

## 8. 怎么判断改造有效

别用"感觉记性变好"这种指标。用三个可测的：

| 指标 | 怎么测 | 目标 |
| --- | --- | --- |
| **重复踩坑率** | 同类错误在 N 次会话内重复出现 | 从"每会话 1-2 次"降到"每月 1 次" |
| **L4 占用** | `wc -l` 开局注入内容 | ≤ 200 行，且**有守卫测试** |
| **检索命中** | 遇到问题时，能否一次在 L3 找到答案 | 抽 10 个真实问题，≥ 7 次直接命中 |

---

## 9. 与文章的一处刻意分歧

文章强调"强模型不要用死板规则约束"。**我保留一条硬规则**：

> 任何"修好了"的结论，必须附**根因 / 改法 / 证据**三样（测试名 + commit）。

理由：这是 `output/REPLY-RULES.md` 里已经吃过亏总结出来的，而且它不是"限制记什么"，而是**要求可验证**——属于文章的"保留原始底账"原则，不矛盾。
